## Usage

Document defaults support sustained reading and return visits. The documentation rules below apply to self-service and technical pages, not to every report.

## Rules

- For a paginated document meant to be read, printed, or filed, set the fixed page dimensions before composing the content.
- In a long paginated document, provide a header or footer identifying the entity, section, or page position when needed for navigation, citation, or return reading; a memo or one-pager need not have one.
- Include a table of contents only when the document is long enough that readers need help navigating between sections.
- Every page that carries data carries its source citation; attribute chart sources directly.
- Use one body-reading column in documentation.
- Name the task in a how-to title and state who it is for and what it completes before the first step; name the linked subject in a directory title.
- Show where a documentation page sits and end with a next move: link the next page by title in a sequence, or the related pages that follow when the sequence ends.
- Give documentation pages long enough to scroll section jump links; break a long how-to into sections the reader can open.
- Give a directory a scope sentence, grouped entries, and links that name their destination and contents.
- Provide search where a documentation collection is too large to browse.
- Use an instructional image only when it teaches something the text cannot.
- Put each warning at the step it concerns, using a callout or sentence according to the consequence.
- After self-service options and before the footer, give problem-solving pages a support contact or an explicit next action when no support channel exists.
- If asking whether a page helped, use one quiet feedback row rather than a survey.
- Preserve the same header, navigation, and footer across a document set; update current-page, open-section, and breadcrumb states rather than redesigning them.
- Address technical documentation to the person building the integration.
- Make code samples complete enough to run, with real endpoints and field names; explicitly name anything the reader must supply.
- Put code in copyable monospace blocks.
- Give reference parameters consistent table columns: name, type, whether required, and purpose.
- Use prose around code to explain why the step exists, what breaks without it, and what to check before continuing.
- In technical documentation, show the current page in a persistent section tree for the document set.
- Use line drawings to explain interface relationships schematically; use authentic material for anything presented as a real product screen.

## Never

- Never put marketing heroes, benefit copy, promotional modules, or upsells inside documentation — instead lead with the answer or steps.
- Never wrap documentation lists and paragraphs in unnecessary cards — instead use plain sections, headings, and links.
- Never publish code as a screenshot — instead provide a block the reader can copy.
